# 03. Данные

Статус: корпус, предобработка и индекс описаны; benchmark — впереди.

## Корпус

Файл `code/data/mods.jsonl` (`D-08`, `GAP-17`): одна строка — один документ, кодировка UTF-8. Рядом лежит `code/data/mods.meta.json` с параметрами и датой выгрузки, числом документов и запросов.

Состав: 1000 самых скачиваемых проектов типа `mod` на Modrinth на дату выгрузки (рабочее допущение `GAP-17`). Строки упорядочены по убыванию `downloads`, при равенстве — по `id`.

Поля документа — из `../Product/05-rules-and-data-meaning.md`, раздел 2.6:

| Поле | Тип | Откуда |
| ---- | --- | ------ |
| `id`, `slug` | строка | `id`, `slug` проекта |
| `title`, `description` | строка | как у автора, пробелы схлопнуты |
| `body` | строка | полное описание, очищенное по `RULE-DATA-05` (см. ниже) |
| `categories`, `loaders`, `game_versions` | список строк | как у проекта; в поиске не участвуют (`RULE-DATA-04`) |
| `url` | строка | `https://modrinth.com/mod/{slug}` (`RULE-UI-04`) |
| `downloads` | число | число скачиваний на дату выгрузки |

Моды-библиотеки и описания не на английском пока остаются в корпусе (`GAP-04`).

## Выгрузка

Скрипт `code/scripts/fetch_modrinth.py`, только стандартная библиотека Python 3.12:

```bash
python3 code/scripts/fetch_modrinth.py            # 1000 модов в code/data/mods.jsonl
python3 code/scripts/fetch_modrinth.py --limit 50 --out /tmp/probe.jsonl
```

1. `GET /v2/search` с `facets=[["project_type:mod"]]`, `index=downloads`, страницами по 100 — список `id`.
2. `GET /v2/projects?ids=[…]` пакетами по 100 — полные проекты с `body`.
3. Остаются только проекты с `project_type = mod` (`RULE-DATA-01`), запись идёт через временный файл.

Ограничения Modrinth: `User-Agent` берётся из `MODRINTH_USER_AGENT` (окружение или `.env`), без него скрипт не запускается; запросы идут не чаще одного в 0,25 с (240 в минуту при лимите 300), на ответ `429` скрипт ждёт время из `Retry-After` / `X-Ratelimit-Reset`, на ошибки `5xx` и сети повторяет запрос до 5 раз. Выгрузка 1000 модов — около 20 запросов.

Очистка `body` (`RULE-DATA-05`, функция `clean_body`): удаляются HTML-комментарии, строки ограждения кода, картинки markdown вместе с подписью, адреса ссылок (текст ссылки остаётся), определения ссылок, HTML-теги (текст внутри остаётся), голые адреса `http…`/`www.`, горизонтальные линии, маркеры списков, разделители таблиц и символы разметки (`#`, `*`, `_`, `~`, обратная кавычка, `>`, `|`, `\`); HTML-сущности раскрываются, пробелы схлопываются в один. Результат — одна строка. Проверки — `code/tests/test_fetch_modrinth.py`.

Дата и параметры выгрузки записаны в `mods.meta.json` и `../Service/sources.md` (`RULE-DATA-07`).

## Предобработка текста

Код — `code/search/preprocess.py`. Документы и запросы проходят одну и ту же обработку (методичка, замечание 1.1; `RULE-SRCH-02`). Индексируемый текст документа — `title`, `description` и `body` через перевод строки (`RULE-DATA-03`).

| Шаг | Что делаем | Обоснование (`RULE-SRCH-07`) |
| --- | ---------- | ---------------------------- |
| Нижний регистр | весь текст приводится к нижнему регистру | Методичка, раздел 1.1, и презентация «Занятие 3», слайд 9. Регистр в описаниях модов смысла не несёт: `FPS`, `fps` и `Fps` — одно и то же |
| Токенизация | токен — отдельное слово: непрерывная последовательность букв и цифр (`[^\W_]+`, любой алфавит); пунктуация, дефисы, подчёркивания и прочие символы — разделители | Методичка, раздел 1.2: «положим, что токеном является отдельное слово»; слайд 9 — «без пунктуации». Разбиение по дефису делает `auto-farm` равным `auto farm`; числа сохраняются как токены (`1`, `20`), но в запросах редки и из-за высокого `df` весят мало |
| Лемматизация | готовая библиотека `simplemma` 2.0.0, английский словарь: `farms`, `farming` → `farm`, `mobs` → `mob`, `shaders` → `shader`; слова не из словаря (названия модов, русские слова) не меняются | Методичка, раздел 2, разрешает готовые библиотеки лемматизации. Корпус английский (`GAP-01`), а запрос игрока и описание мода часто различаются формой слова: без лемматизации `farming` ≠ `farm` (как «билет» ≠ «билета» на слайде 9) и Recall падает. `simplemma` — словарный лемматизатор без внешних моделей и сетевых загрузок; стемминг отклонён, потому что обрезает слова до не-слов (`storage` → `storag`) и хуже читается в разборе вкладов |
| Стоп-слова | не удаляются | В презентации стоп-слова не удаляются (слайд 11: «как» и «происходит» остаются), а формула IDF сама даёт частым словам малый вес: в корпусе модов `and` получает ≈ 0,1 против 4–8 у `farm`, `spell`, `fps`. Так поиск не зависит от выбора списка стоп-слов. На benchmark удаление 125 служебных слов (`ENGLISH_STOPWORDS`) подняло Recall@5 с 0,567 до 0,600, но снизило MRR@5 с 0,775 до 0,687, поэтому не принято |

Лемматизацию можно отключить (`Preprocessor(no_lemmatize)`), чтобы сравнить варианты на benchmark.

## Индекс

Собственная реализация BM25 (`RULE-SRCH-01`) — `code/search/bm25.py`, по формуле методички (раздел 1.3) и коду презентации «Занятие 3» (слайды 25–28):

- обратный индекс `терм → {id документа: tf}` и длины документов в термах; `N` и `avgdl` считаются по ним;
- `IDF(t) = ln(1 + (N − df + 0,5) / (df + 0,5))` — всегда положителен, поэтому каждый документ хотя бы с одним совпадением получает балл больше нуля, а документы без совпадений в выдачу не попадают (`RULE-SRCH-05`);
- повторы слов в запросе учитываются один раз (`dict.fromkeys`, слайд 26);
- сортировка по убыванию балла, при равенстве — по `id` (`RULE-SRCH-03`, слайды 24 и 28); выдаются первые `k = 5` (`RULE-SRCH-04`);
- параметры `k1 = 1,2` (`GAP-03`, подбирается по benchmark) и `b = 0,75` (`RULE-SRCH-06`);
- для каждого документа выдачи сохраняется вклад каждого слова запроса — для разбора ошибок benchmark (слайд 5: «можно объяснить каждый балл»).

На снимке 2026-11-17: 1000 документов, 13 990 термов, `avgdl` ≈ 353 терма, построение ≈ 0,7 с.

Файл индекса — `code/data/index.json` (JSON, в Git не попадает, строится из корпуса): формат, предобработка, `k1`, `b`, `meta` (имя и SHA-256 корпуса), `lengths`, `index`. При старте индекс загружается из файла целиком в память, если он построен по тому же корпусу и с той же предобработкой; иначе строится заново и сохраняется (`ModSearch.open`).

Интерфейс для бэкенда (`GAP-07`) — модуль вызывается как библиотека в одном процессе:

```python
from search import ModSearch            # каталог code/ в sys.path
engine = ModSearch.open()               # code/data/mods.jsonl + index.json
for doc, hit in engine.search(query_en, k=5):
    doc["slug"], doc["title"], doc["url"], hit.score, hit.contributions
```

Запрос передаётся уже на английском: перевод русского запроса (`GAP-01`) выполняет бэкенд до вызова поиска (`RULE-SRCH-02`).

Командная строка (из каталога `code/`):

```bash
python -m pip install -r search/requirements.txt
python -m search build                              # построить index.json
python -m search --explain "automate farm without lag"
python -m pytest tests
```

## Восстановление

Индекс можно перестроить из корпуса: `python -m search build` или удалить `code/data/index.json` — он будет построен при следующем `ModSearch.open()`.
