# Minecraft Mod Picker — смысл данных и правила

## 1. Назначение документа

Документ объясняет, что означают данные, с которыми работает приложение, откуда они берутся, и содержит пронумерованные правила для интерфейса, поиска, ответа и проверки качества.

Правило имеет идентификатор вида `RULE-ГРУППА-NN`. Идентификаторы не переиспользуются и не перенумеровываются.

Значения, помеченные «(предложение)», приняты по умолчанию и подтверждаются в `../Service/decisions.md` (раздел «Открытые вопросы», GAP-03).

## 2. Смысл данных

### 2.1. Запрос

Текст задачи, который ввёл игрок. Перед поиском проходит ту же предварительную обработку, что и документы корпуса.

### 2.2. Документ

Документ — один мод (проект типа `mod` на Modrinth). Из документа используются название, короткое описание, полное описание, категории и ссылка.

### 2.3. Корпус и индекс

Корпус — зафиксированный набор документов (снимок). Индекс — структура данных BM25, построенная из корпуса: хранит соответствие между термами и документами.

### 2.4. Результат поиска

Упорядоченный по убыванию оценки BM25 список из первых `k` документов. У каждого документа в результате есть оценка релевантности.

### 2.5. Ответ с объяснением

Короткий текст, который формирует LLM по запросу и найденным документам. Ответ не должен упоминать моды, которых нет в результате поиска.

### 2.6. Поля документа

| Поле                       | Смысл                                                                  | Где используется                            |
| -------------------------- | ---------------------------------------------------------------------- | ------------------------------------------- |
| `id`, `slug`               | Идентификатор и короткое имя проекта на Modrinth                       | связь с разметкой benchmark, ссылка         |
| `title`                    | Название мода                                                          | индекс, карточка                            |
| `description`              | Короткое описание автора                                               | индекс, карточка                            |
| `body`                     | Полное описание автора, очищенное от разметки                          | индекс                                      |
| `categories`               | Категории Modrinth (storage, food, optimization и др.)                 | карточка, подсказка при разметке benchmark  |
| `loaders`, `game_versions` | Загрузчики и версии игры                                               | сохраняются, в поиске не участвуют (GAP-02) |
| `url`                      | Ссылка на страницу мода                                                | карточка                                    |
| `downloads`                | Число скачиваний на дату выгрузки                                      | сортировка при выгрузке                     |

### 2.7. Учётная запись и роль

Учётная запись — пара «логин и пароль», по которой человек входит в приложение. Их ровно две: у администратора и у пользователя. Роль учётной записи определяет, какой экран доступен: пользователю — экран поиска, администратору — админ-панель. Данные для входа задаются администратором системы вне интерфейса (GAP-09).

### 2.8. Числовая аналитика

Числовые показатели использования приложения, которые видит администратор в админ-панели. Сейчас показатель один — счётчик запросов: сколько поисковых запросов выполнил пользователь. Что именно считается запросом, определяет `RULE-ADM-02`. Набор показателей может расширяться (GAP-12). Тексты запросов администратору не показываются.

### 2.9. Источник

Публичный API Modrinth v2. Подробности и дата выгрузки: `../Service/sources.md`. Тексты описаний принадлежат авторам модов. Корпус — снимок на дату выгрузки и не обновляется автоматически.

## 3. Правила: данные

| ID           | Правило                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- |
| RULE-DATA-01 | Документ — один мод: проект типа `mod` на Modrinth.                                                                       |
| RULE-DATA-03 | Индексируемый текст документа — название, короткое описание и очищенное полное описание (`title`, `description`, `body`). |
| RULE-DATA-04 | Для документа хранятся поля из раздела 2.6. Поля `categories`, `loaders` и `game_versions` в поиске не участвуют.         |
| RULE-DATA-05 | Полное описание перед индексацией очищается от картинок, ссылок, HTML-тегов и символов разметки.                          |
| RULE-DATA-06 | Мода, которого нет в снимке, для системы не существует: он не может попасть в выдачу или в ответ.                         |
| RULE-DATA-07 | Источник данных и дата выгрузки указаны в `../Service/sources.md`.                                                        |

## 4. Правила: поиск

| ID           | Правило                                                                                                                                                   |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RULE-SRCH-01 | Поиск выполняется собственной реализацией BM25. Готовые поисковые индексы и движки не используются.                                                       |
| RULE-SRCH-02 | Запрос проходит ту же предварительную обработку, что и документы. Если принято решение о переводе запроса (GAP-01), перевод выполняется до предобработки. |
| RULE-SRCH-03 | Документы упорядочиваются по убыванию оценки BM25.                                                                                                        |
| RULE-SRCH-04 | В выдачу попадают первые `k` документов, `k = 5` (предложение). Значение настраивается.                                                                   |
| RULE-SRCH-05 | Документы с нулевой оценкой в выдачу не попадают.                                                                                                         |
| RULE-SRCH-06 | Параметры BM25 настраиваются: `k1 = 1.5`, `b = 0.75` по умолчанию (предложение). Значения подбираются по результатам benchmark.                           |
| RULE-SRCH-07 | Выбранные способы токенизации, нормализации и (не)лемматизации обоснованы в `../Tech/03-data.md`.                                                         |

## 5. Правила: ответ с объяснением

| ID          | Правило                                                                                                  |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| RULE-ANS-01 | LLM получает запрос игрока и только документы из выдачи.                                                 |
| RULE-ANS-02 | Ответ не называет и не рекомендует моды, которых нет в выдаче.                                           |
| RULE-ANS-03 | Ответ формируется на русском языке (GAP-01).                                                             |
| RULE-ANS-04 | Если LLM недоступна, карточки модов всё равно показываются, а вместо ответа выводится сообщение об этом. |
| RULE-ANS-05 | Ответ краткий: ориентир — до 150 слов (предложение).                                                     |

## 6. Правила: интерфейс

| ID         | Правило                                                                                                                                             |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| RULE-UI-01 | Пустой запрос и запрос из одних пробелов не отправляются на поиск. Показывается подсказка «Опишите задачу, чтобы начать поиск».                     |
| RULE-UI-02 | Максимальная длина запроса — 500 символов (предложение).                                                                                            |
| RULE-UI-04 | Карточка мода содержит название, короткое описание, категории и ссылку вида `https://modrinth.com/mod/{slug}`, которая открывается в новой вкладке. |
| RULE-UI-05 | Повторный поиск заменяет предыдущие результаты. Выбор примера запроса подставляет текст в поле и сразу запускает поиск.                             |

## 7. Правила: ошибки и пустые состояния

| ID          | Правило                                                                                        |
| ----------- | ---------------------------------------------------------------------------------------------- |
| RULE-ERR-01 | При ошибке игрок видит понятное сообщение без технических деталей и может повторить запрос.    |
| RULE-ERR-02 | Если подходящих документов нет, игрок видит сообщение с предложением переформулировать задачу. |

## 8. Правила: проверка качества

| ID         | Правило                                                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| RULE-QA-01 | Качество поиска оценивается метриками Recall@k и MRR на тестовом наборе запросов.                                                  |
| RULE-QA-02 | Для каждого тестового запроса определено не менее трёх релевантных документов.                                                     |
| RULE-QA-03 | Тестовый набор равномерно покрывает содержание корпуса. Запросы формулируются своими словами, а не копированием фрагментов текста. |
| RULE-QA-04 | Benchmark воспроизводим: корпус зафиксирован, разметка релевантности привязана к `id` документов.                                  |
| RULE-QA-05 | Результаты каждого запуска benchmark записываются в `../Service/verification.md`.                                                  |

## 9. Правила: вход и доступ

| ID           | Правило                                                                                                                                                                                                                                                                                                                             |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RULE-AUTH-01 | В системе ровно две учётные записи: администратор и пользователь. Регистрации, создания и удаления учётных записей, смены и восстановления пароля через интерфейс нет.                                                                                                                                                              |
| RULE-AUTH-02 | Вход выполняется по логину и паролю. Данные для входа обеих учётных записей хранятся только в окружении (`.env`), в репозиторий не попадают; в `.env.example` перечислены переменные без значений (GAP-09).                                                                                                                         |
| RULE-AUTH-03 | Пустой логин или пароль не проверяются, показывается «Введите логин и пароль». При неверных данных показывается «Неверный логин или пароль» без уточнения, что именно неверно; поле пароля очищается.                                                                                                                               |
| RULE-AUTH-04 | После входа открывается экран по роли: пользователю — экран поиска, администратору — админ-панель.                                                                                                                                                                                                                                  |
| RULE-AUTH-05 | Без входа доступен только экран входа. Экран поиска доступен только пользователю, админ-панель — только администратору. При попытке открыть недоступный экран показывается экран входа (если вход не выполнен) или экран своей роли (GAP-11). Проверка выполняется на стороне сервера, а не только скрытием элементов в интерфейсе. |
| RULE-AUTH-06 | «Выйти» завершает сессию. После выхода защищённые экраны недоступны, пока человек не войдёт снова. Срок жизни сессии без выхода — GAP-11.                                                                                                                                                                                           |

## 10. Правила: админ-панель

| ID          | Правило                                                                                                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RULE-ADM-01 | Админ-панель показывает числовую аналитику. Сейчас единственный показатель — общее число поисковых запросов пользователя. Набор показателей может расширяться (GAP-12). Тексты запросов в панели не показываются.                                                              |
| RULE-ADM-02 | Запросом считается каждая отправка текста на поиск, прошедшая проверки `RULE-UI-01` и `RULE-UI-02`, независимо от исхода (результаты, пустая выдача, ошибка). Пустые запросы и запросы, не прошедшие проверку, не считаются. Запрос из примера считается как обычный (GAP-10). |
| RULE-ADM-03 | Число считается за всё время работы системы и увеличивается на 1 при каждом запросе по `RULE-ADM-02`. Способ хранения и сохранение между перезапусками — GAP-10.                                                                                                               |
