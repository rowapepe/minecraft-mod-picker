# Minecraft Mod Picker — смысл данных и правила

## 1. Назначение документа

Документ объясняет, что означают данные, с которыми работает приложение, откуда они берутся, и содержит пронумерованные правила для интерфейса, поиска, ответа и проверки качества.

Правило имеет идентификатор вида `RULE-ГРУППА-NN`. Идентификаторы не переиспользуются и не перенумеровываются.

Числовые значения поиска и ответа подтверждены решением `D-31` (`../Service/decisions.md`).

## 2. Смысл данных

### 2.1. Запрос

Текст задачи, который ввёл игрок. Перед поиском проходит ту же предварительную обработку, что и документы корпуса.

### 2.2. Документ

Документ — один мод (проект типа `mod` на Modrinth). Из документа используются название, короткое описание, полное описание, категории и ссылка.

### 2.3. Корпус и индекс

Корпус — зафиксированный набор документов (снимок). Индекс — структура данных BM25, построенная из корпуса: хранит соответствие между термами и документами.

### 2.4. Результат поиска

Упорядоченный по убыванию оценки BM25 список из первых `k` документов. У каждого документа в результате есть оценка релевантности.

### 2.5. Ответ с объяснением

Короткий текст, который формирует LLM по запросу и найденным документам. Ответ не должен упоминать моды, которых нет в результате поиска.

### 2.6. Поля документа

| Поле                       | Смысл                                                  | Где используется                            |
| -------------------------- | ------------------------------------------------------ | ------------------------------------------- |
| `id`, `slug`               | Идентификатор и короткое имя проекта на Modrinth       | связь с разметкой benchmark, ссылка         |
| `title`                    | Название мода                                          | индекс, карточка                            |
| `description`              | Короткое описание автора                               | индекс, карточка                            |
| `body`                     | Полное описание автора, очищенное от разметки          | индекс                                      |
| `categories`               | Категории Modrinth (storage, food, optimization и др.) | карточка, подсказка при разметке benchmark  |
| `loaders`, `game_versions` | Загрузчики и версии игры                               | сохраняются, в поиске не участвуют (GAP-02) |
| `url`                      | Ссылка на страницу мода                                | карточка                                    |
| `downloads`                | Число скачиваний на дату выгрузки                      | сортировка при выгрузке                     |

### 2.7. Учётная запись и роль

Учётная запись — пара «логин и пароль», по которой человек входит в приложение. Их ровно две: у администратора и у пользователя. Роль учётной записи определяет, какой экран доступен: пользователю — экран поиска, администратору — админ-панель. Данные для входа задаются администратором системы вне интерфейса (`D-23`).

### 2.8. Числовая аналитика

Числовые показатели использования приложения, которые видит администратор в админ-панели. Показываются четыре показателя:

- **число поисковых запросов** — сколько запросов выполнил пользователь (`RULE-ADM-02`, `RULE-ADM-03`);
- **число входов** — сколько раз человек успешно вошёл в приложение (`RULE-ADM-04`);
- **запросы по дням** — сколько запросов пришлось на каждый из последних семи календарных дней, включая дни без запросов (`RULE-ADM-05`);
- **доля запросов без результатов** — отношение запросов с пустой выдачей к числу всех запросов (`RULE-ADM-06`).

Тексты запросов администратору не показываются. Счётчики хранятся на сервере и не сбрасываются при перезапуске (`RULE-ADM-03`); в заглушке API для разработки они лежат в `code/frontend/.dev-stub/analytics.json` (`D-15`). Постоянное хранилище реального бэкенда — `GAP-16`.

### 2.9. Источник

Публичный API Modrinth v2. Подробности и дата выгрузки: `../Service/sources.md`. Тексты описаний принадлежат авторам модов. Корпус — снимок на дату выгрузки и не обновляется автоматически.

### 2.10. Контекст запроса и костюм зомби

Контекст запроса — тема задачи, которую интерфейс определяет по словам в тексте запроса. По теме выбирается костюм талисмана «Зомби» (`RULE-MASCOT-02`). Поиск и ответ от темы не зависят.

Слово запроса (после приведения к нижнему регистру, `ё` заменяется на `е`; слова разделяются любыми символами, кроме букв и цифр) совпадает с ключевым, если начинается с него. Ключевое слово со знаком `$` на конце совпадает только с целым словом.

Костюмы перечислены в порядке приоритета (при равенстве числа совпадений выигрывает верхний):

| Костюм            | Ключевые слова                                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ |
| Фермер            | ферм, урожа, кулинар, огород, животн, скот, сельск, кроп, выращ                                                    |
| Оптимизатор       | fps, лаг, тормоз, оптимиз, производит, слаб, ram$, памят                                                           |
| Любитель шейдеров | шейдер, графи, текстур, красив, тени$, тень$, shader                                                               |
| Маг               | маги, магич, заклин, колдов, волшеб, ритуал, мана$                                                                 |
| Рыцарь            | бой$, бои$, боев, сраж, оружи, меч$, мечи$, босс, враг, моб$, мобы$, мобов$, pvp, пвп, combat, войн                |
| Шахтёр            | шахт, руд, копа, добыч, пещер, алмаз, генерац, приключ, исследов, подзем                                           |
| Строитель         | строит, дом$, дома$, доме$, домов$, декор, мебел, хран, сундук, склад, схем, постройк, архитект, автомат, редстоун |
| Без костюма       | совпадений нет или запроса нет                                                                                     | «Привет! Опиши задачу, а я подберу моды.» |

Набор костюмов и слов принят (`D-27`); список расширяется добавлением строки в таблицу и в `code/frontend/src/mascot/costumes.ts`.

### 2.11. Чат и сообщение

Чат — набор сообщений, отправленных подряд в одной беседе. Каждое сообщение — это запрос игрока с состоянием и результатом: загрузка, ответ, пустая выдача или ошибка. Заголовок чата — текст первого сообщения.

Список чатов хранится локально в браузере, после перезагрузки восстанавливается; на сервер не сохраняется и администратору не показывается. Продолжение чата добавляет новое сообщение в открытый чат, а не создаёт новую запись списка. Предыдущие сообщения не передаются как контекст LLM: каждый поиск выполняется только по тексту нового сообщения.

## 4. Правила: поиск

| ID           | Правило                                                                                                                                                   |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RULE-SRCH-01 | Поиск выполняется собственной реализацией BM25. Готовые поисковые индексы и движки не используются.                                                       |
| RULE-SRCH-02 | Запрос проходит ту же предварительную обработку, что и документы. Запрос с кириллицей переводится LLM в английские ключевые слова до предобработки; запрос без кириллицы идёт в поиск как есть (`D-18`, `D-22`). |
| RULE-SRCH-03 | Документы упорядочиваются по убыванию оценки BM25.                                                                                                        |
| RULE-SRCH-04 | В выдачу попадают первые `k` документов, `k = 5` (`D-31`). Значение настраивается.                                                                   |
| RULE-SRCH-05 | Документы с нулевой оценкой в выдачу не попадают.                                                                                                         |
| RULE-SRCH-06 | Параметры BM25: `k1 = 1.2`, `b = 0.75` (`D-31`). Значение `k1 = 1.2` совпадает с кодом и примером расчёта в презентации «Занятие 3»; первый прогон benchmark значимой разницы между 1.2, 1.5 и 2.0 не показал. Параметры настраиваются. |
| RULE-SRCH-07 | Выбранные способы токенизации, нормализации и (не)лемматизации обоснованы в `../Tech/03-data.md`.                                                         |

## 5. Правила: ответ с объяснением

| ID          | Правило                                                                                                  |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| RULE-ANS-01 | LLM получает запрос игрока и только документы из выдачи.                                                 |
| RULE-ANS-02 | Ответ не называет и не рекомендует моды, которых нет в выдаче.                                           |
| RULE-ANS-03 | Ответ формируется на русском языке (`D-22`).                                                             |
| RULE-ANS-04 | Если LLM недоступна, карточки модов всё равно показываются, а вместо ответа выводится сообщение об этом. |
| RULE-ANS-05 | Ответ краткий: ориентир — до 150 слов (`D-31`).                                                     |
| RULE-ANS-06 | Если в описаниях найденных модов нет ответа на запрос, вместо объяснения выводится отказ — текст «В описаниях найденных модов нет ответа на этот вопрос.» вместе с найденными модами; ответ не придумывается (`D-19`, `D-29`). |

## 6. Правила: интерфейс

| ID         | Правило                                                                                                                                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RULE-UI-01 | Пустой запрос и запрос из одних пробелов не отправляются на поиск. Показывается подсказка «Опишите задачу, чтобы начать поиск».                                                                                                |
| RULE-UI-02 | Максимальная длина запроса — 500 символов (`D-31`).                                                                                                                                                                       |
| RULE-UI-04 | Карточка мода содержит название, короткое описание, категории и ссылку вида `https://modrinth.com/mod/{slug}`, которая открывается в новой вкладке.                                                                            |
| RULE-UI-05 | Новый чат заменяет предыдущий вид в основной области. Выбор примера запроса сразу отправляет его текст как запрос нового чата.                                                                                                  |
| RULE-UI-06 | Боковая панель раскрытая или свёрнутая; переключается кнопкой; на экране шириной до 760 px по умолчанию скрыта и открывается поверх страницы. Вид панели не сохраняется между загрузками.                                      |

| RULE-UI-08 | «Новый поиск» показывает пустое состояние и очищает поле, не удаляя список чатов.                                                                                                                                              |
| RULE-UI-09 | Пока в списке нет чатов, в его середине показан скелет и подпись «Нет чатов».                                                                                                                                                  |
| RULE-UI-10 | Поиск запускается кнопкой «Найти моды», клавишами Enter, Ctrl+Enter и Cmd+Enter; Shift+Enter переносит строку. Во время поиска отправка недоступна.                                                                            |
| RULE-UI-11 | Если чат открыт, отправка нового запроса добавляет сообщение в этот чат: предыдущие сообщения остаются выше, запись списка не создаётся. Если открытого чата нет, создаётся новый чат с заголовком из текста запроса.          |
| RULE-UI-12 | Переключатель тёмной и светлой темы виден на экране входа, экрана поиска и админ-панели. Кнопка размером 48 × 48 px со значком 24 × 24 px. Выбранная тема сохраняется в браузере и применяется после перезагрузки.             |

### Талисман

| ID             | Правило                                                                                                                                                                                                                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RULE-MASCOT-01 | На экране поиска над формой справа стоит талисман — мини-зомби. Он расположен поверх ленты: за ним видны сообщения чата, отдельная полоса под талисман не выделяется. Талисман декоративный: имя и реплика не показываются, на поиск и счётчик он не влияет и скрыт от скринридера. На экране входа зомби без костюма стоит на карточке входа. |
| RULE-MASCOT-02 | Костюм определяется по тексту открытого запроса (раздел 2.10): для каждого костюма считается число слов запроса, совпавших с ключевыми; выигрывает костюм с наибольшим числом, при равенстве — стоящий выше в таблице; без совпадений — без костюма. |
| RULE-MASCOT-03 | Костюм меняется в момент отправки запроса и при выборе записи списка (по её запросу). В пустом состоянии, после «Нового поиска» и до первого запроса зомби без костюма.                                                                              |
| RULE-MASCOT-04 | Пока идёт поиск, зомби качается быстрее.                                                                                                                                                            |
| RULE-MASCOT-05 | Отменено (`D-21`): имя и реплика зомби не показываются.                                                                                                                                                                     |
| RULE-MASCOT-06 | При настройке системы «уменьшить движение» анимации зомби, скелета и индикатора загрузки отключаются.                                                                                                                                                |

| ID          | Правило                                                                                        |
| ----------- | ---------------------------------------------------------------------------------------------- |
| RULE-ERR-01 | При ошибке игрок видит понятное сообщение без технических деталей и может повторить запрос.    |
| RULE-ERR-02 | Если подходящих документов нет, игрок видит сообщение с предложением переформулировать задачу. |

## 8. Правила: проверка качества

| ID         | Правило                                                                                                                            |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| RULE-QA-01 | Качество поиска оценивается на зафиксированном тестовом наборе (30 документов, 10 обычных вопросов и 5 вопросов-ловушек) четырьмя метриками: Recall@k и MRR — по обычным вопросам, Accuracy — по обычным вопросам, Correct Rejection Rate — по ловушкам (`D-32`). |
| RULE-QA-02 | Для каждого обычного тестового запроса определено не менее трёх релевантных документов и эталон; для вопросов-ловушек ожидается отказ (`D-32`). |
| RULE-QA-03 | Тестовый набор равномерно покрывает содержание корпуса. Запросы формулируются своими словами, а не копированием фрагментов текста. |
| RULE-QA-04 | Benchmark воспроизводим: корпус зафиксирован, разметка релевантности привязана к `id` документов.                                  |
| RULE-QA-05 | Результаты каждого запуска benchmark записываются в `../Service/verification.md`.                                                  |

| RULE-AUTH-04 | После входа открывается экран по роли: пользователю — экран поиска, администратору — админ-панель.                                                                                                                                                                                                                                  |

| RULE-AUTH-06 | «Выйти» завершает сессию. После выхода защищённые экраны недоступны, пока человек не войдёт снова. Без выхода сессия действует до закрытия браузера (`D-25`).                                                                                                                                                                                           |

## 10. Правила: админ-панель

| ID          | Правило                                                                                                                                                                                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RULE-ADM-01 | Админ-панель показывает четыре числовых показателя: общее число поисковых запросов, число входов, запросы по дням и долю запросов без результатов. Тексты запросов в панели не показываются.                                                                                    |
| RULE-ADM-02 | Запросом считается каждая отправка текста на поиск, прошедшая проверки `RULE-UI-01` и `RULE-UI-02`, независимо от исхода (результаты, пустая выдача, ошибка). Пустые запросы и запросы, не прошедшие проверку, не считаются. Запрос из примера считается как обычный (`D-24`). |
| RULE-ADM-03 | Число считается за всё время работы системы и увеличивается на 1 при каждом запросе по `RULE-ADM-02`.
