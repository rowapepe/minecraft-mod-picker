# Minecraft Mod Picker — контекст

## 1. Назначение документа

Документ описывает Minecraft Mod Picker как продукт: зачем он нужен, какие задачи решает и какие границы у текущей версии.

Документ предназначен в первую очередь для человека: преподавателя, участника команды или нового разработчика, которому нужно быстро понять смысл системы до чтения сценариев, интерфейса и правил.

Подробности: роли и сценарии — `02-users-and-scenarios.md`, требования — `03-requirements.md`, интерфейс — `04-interface-and-behavior.md`, данные и правила — `05-rules-and-data-meaning.md`.

## 2. Краткое описание

Minecraft Mod Picker — веб-приложение для подбора модов Minecraft под задачу игрока.

Игрок описывает задачу обычными словами, например «хочу автоматизировать ферму и не получить лагов». Система ищет подходящие моды по их описаниям с Modrinth, показывает карточки найденных модов и формирует короткий ответ, который объясняет, почему эти моды подходят.

Поиск выполняется собственной реализацией модели BM25. Ответ формирует LLM, но только на основе найденных документов.

Доступ к приложению — по логину и паролю. В системе ровно две учётные записи: пользователь (ищет моды) и администратор (смотрит в панели числовую аналитику, сейчас — число поисковых запросов). Регистрации нет.

Система не заменяет изучение страницы мода и не гарантирует, что мод совместим с версией игры или сборкой игрока. Она помогает быстро получить список кандидатов и понять, чем они полезны.

## 3. Контекст продукта

Minecraft Mod Picker — самостоятельное веб-приложение с двумя фиксированными учётными записями (администратор и пользователь) и без регистрации.

Данные:

- Описания модов берутся из публичного API Modrinth (v2) и сохраняются как зафиксированный снимок корпуса.
- Во время работы приложение к Modrinth не обращается. Поиск идёт по локальному снимку.

Компоненты:

- Интерфейс: один основной экран.
- Поиск: индекс BM25, построенный из корпуса.
- LLM: внешний сервис, используется для формирования ответа и, при принятии соответствующего решения, для перевода запроса (GAP-01).

Контекст проекта: учебная работа НИРС 2026. Качество поиска измеряется на собственном тестовом наборе запросов (Recall@k, MRR).

## 4. Основная пользовательская ценность

Каталог Modrinth удобно искать, когда известно название или категория мода. Игроку, который знает свою задачу, но не знает, какие моды для неё существуют, приходится перебирать каталог вручную.

Вместо этого игрок описывает задачу своими словами и получает:

- список подходящих модов, упорядоченный по релевантности;
- краткое объяснение, почему они подходят, чтобы быстро сравнить кандидатов;
- прямую ссылку на страницу каждого мода.

## 5. Область применения

### 5.1. Входит в текущий объём

- Экран входа: логин, пароль, кнопка «Войти».
- Две фиксированные учётные записи: администратор и пользователь.
- Экран поиска для пользователя: поле ввода задачи и кнопка поиска.
- Админ-панель для администратора: числовая аналитика запросов пользователя.
- Выход из системы.
- Примеры запросов для быстрого старта.
- Поиск по корпусу собственной реализацией BM25.
- Показ найденных модов карточками.
- Ответ с объяснением на основе найденных документов.
- Ссылка с каждой карточки на страницу мода на Modrinth.
- Понятные сообщения для пустого запроса, пустой выдачи и ошибок.
- Тестовый набор запросов и расчёт метрик качества поиска.

### 5.2. Не входит в текущий объём

- Регистрация, создание и удаление учётных записей, смена и восстановление пароля.
- История запросов пользователя и просмотр текстов запросов.
- Проверка совместимости модов между собой, с версией игры и со сборкой.
- Скачивание модов и установка.
- Автоматическое обновление корпуса.
- Гарантия полноты и точности подбора.

## 6. Ограничения текущего этапа

- Язык: принято рабочее допущение, что корпус и поиск работают на английском, а интерфейс и ответ на русском; русский запрос предварительно переводится в английские ключевые слова. Решение подтверждается в GAP-01.
- Фильтрации по версии игры и загрузчику в первой версии нет (GAP-02).
- Контрольная точка 1: нужно определиться с темой, разработать дизайн (готовый фронт или макет) и подготовить документацию в формате md. Работа интерфейса на демонстрационных данных не требуется.
- Ответ LLM может содержать неточности. Игрок проверяет детали на странице мода.
- Ключ LLM и данные для входа обеих учётных записей хранятся только в окружении (`.env`) и не попадают в репозиторий (GAP-09).

## 7. Общая логика работы

Вход:

1. Человек открывает приложение. Без входа доступен только экран входа.
2. Он вводит логин и пароль и нажимает «Войти».
3. Система проверяет данные. Пользователь попадает на экран поиска, администратор — в админ-панель. При неверных данных остаётся экран входа с сообщением об ошибке.

Поиск (пользователь):

1. Система показывает экран поиска с полем ввода и примерами запросов.
2. Пользователь вводит задачу или выбирает пример.
3. Пользователь запускает поиск.
4. Система проверяет, что запрос не пустой и не превышает допустимую длину.
5. Система увеличивает счётчик запросов (RULE-ADM-02) и показывает состояние загрузки.
6. Система приводит запрос к форме, пригодной для поиска (предобработка, при необходимости перевод).
7. Система считает оценки BM25 и выбирает первые `k` документов.
8. Система передаёт запрос и найденные документы в LLM и получает ответ с объяснением.
9. Система показывает ответ и карточки модов.
10. Пользователь открывает страницу интересующего мода на Modrinth или повторяет поиск с другой формулировкой.

Админ-панель (администратор):

1. Администратор входит и видит числовую аналитику. Сейчас это число поисковых запросов, выполненных пользователем (состав показателей может расширяться, GAP-12).
2. Чтобы увидеть новые значения, он обновляет страницу.

В любом случае человек может нажать «Выйти» и вернуться на экран входа.
